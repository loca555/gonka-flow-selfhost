# Gonka Flow на своём сервере через IPFS и обычный домен

Версия гайда: 28 октября 2026 года. Цель — адрес вида `https://flow.example.com/#minters`, собственные API и база, интерфейс из IPFS. `flow.example.com` во всех примерах нужно заменить своим доменом. Доступ к доменам проекта или изменение ENS для этого не требуются.

**Схема:** браузер → Caddy с HTTPS → интерфейс из IPFS. Запросы `/api` и `/healthz` Caddy направляет в контейнер Flow. Индексатор Flow получает публичные данные через RPC и сохраняет их в постоянном томе. IPFS хранит статические файлы и не выполняет Python-код API.

## 1 Подготовьте сервер и DNS

Нужен Linux x86_64 с Docker Engine, Compose v2 и Python 3. Стартовый ориентир для всех трёх компонентов — 1–2 vCPU, 2 ГБ RAM и 20 ГБ SSD. Это оценка для небольшого сайта, а не измеренный предел нагрузки. GPU, кошелёк и приватные ключи блокчейна не нужны.

Создайте DNS-запись `A` для своего имени, указывающую на публичный IPv4 сервера. `AAAA` добавляйте только при реально работающем IPv6. Для первого запуска используйте обычную DNS-запись без CDN-проксирования.

Разрешите входящие TCP 80 и 443 для сайта, TCP/UDP 4001 для IPFS. UDP 443 нужен для HTTP/3, но не обязателен для обычного HTTPS. Сохраните доступ по SSH. Порты IPFS API 5001, внутреннего шлюза 8080, Flow 8000 и Caddy admin 2019 в этом Compose наружу не публикуются.

Docker устанавливайте по [официальной инструкции для своей ОС](https://docs.docker.com/engine/install/). Проверьте:

```bash
docker version
docker compose version
python3 --version
```

## 2 Подготовьте каталог

Получите комплект из публичного репозитория и перейдите в его каталог:

```bash
git clone https://github.com/loca555/gonka-flow-selfhost.git
cd gonka-flow-selfhost
sha256sum -c SHA256SUMS
```

Можно также скачать архив через GitHub «Code → Download ZIP» и распаковать его в отдельный пустой каталог сервера. Здесь должны находиться `compose.yaml`, `Caddyfile`, `.env.example`, `init-ipfs.sh` и Python-скрипты.

```bash
cp .env.example .env
chmod 755 init-ipfs.sh
mkdir -p exports backups
```

В `.env` замените только `FLOW_DOMAIN=flow.example.com` на своё имя. Нельзя указывать `https://`, путь, порт или завершающий `/`. Не добавляйте сюда кошельки и ключи. `STACK_NAME` определяет имена Docker-ресурсов; после запуска не меняйте его без переноса данных.

Образ Flow закреплён digest проверенного публичного выпуска от 27 октября 2026 года. Для Kubo и Caddy заданы теги версий. Наличие и возможность скачивания образов на новом сервере проверяет следующая команда:

```bash
docker compose config --quiet
docker compose pull
```

## 3 Пересоберите интерфейс под свой API

Простое закрепление нынешнего CID сохранило бы обращение интерфейса к API проекта. Поэтому сначала извлеките статические файлы из того же образа, который будет обслуживать ваш API. Создание контейнера здесь не запускает приложение:

```bash
SOURCE_DIR="source-$(date -u +%Y%m%dT%H%M%SZ)"
docker compose create flow
docker compose cp flow:/app/app/static "$SOURCE_DIR"
```

Загрузите публичные настройки из созданного вами `.env` в текущую оболочку и соберите отдельную версию сайта:

```bash
set -a
. ./.env
set +a

SITE_NAME="site-$(date -u +%Y%m%dT%H%M%SZ)"
python3 build_front.py \
  --static-dir "$SOURCE_DIR" \
  --api-origin "https://$FLOW_DOMAIN" \
  --output "./exports/$SITE_NAME"
```

Ожидается JSON с вашим API origin и числом файлов. Сборщик переносит только зависимости публичного интерфейса, меняет адреса API и формирует CSP под указанный origin. Каталог извлечения `SOURCE_DIR` и выходной каталог выбирайте новыми: это исключает случайное смешивание разных выпусков. Существующую сборку сборщик не удаляет.

## 4 Закрепите сборку в своей IPFS ноде

```bash
docker compose up -d ipfs
docker compose logs --tail=40 ipfs
docker compose exec -T ipfs ipfs id
```

Дождитесь успешного `ipfs id`, затем добавьте сборку. Если вы открыли новую SSH-сессию, заново задайте `SITE_NAME` именем созданного каталога в `exports`.

```bash
CID=$(docker compose exec -T ipfs ipfs add -Q -r --cid-version=1 --pin=true "/export/$SITE_NAME")
printf '%s\n' "$CID"
docker compose exec -T ipfs ipfs pin ls "$CID"
docker compose exec -T ipfs ipfs cat "/ipfs/$CID/ipfs-build.json"
```

Проверьте, что поле `api` в манифесте содержит именно ваш HTTPS-домен. Сохраните CID. Файлы закреплены в постоянном томе `ipfs-data`; каталог `exports` — только вход для добавления новых версий.

## 5 Свяжите домен с CID через DNSLink

В DNS-панели добавьте TXT-запись для полного имени `_dnslink.flow.example.com`. Значение:

```text
dnslink=/ipfs/ВАШ_CID_ИЗ_ШАГА_4
```

Используйте настоящий CID без кавычек-обёрток и без буквального текста `ВАШ_CID`. В панели, автоматически добавляющей доменную зону, может потребоваться короткое имя `_dnslink.flow`. Для обновлений удобно установить TTL 60–300 секунд.

Проверка с сервера:

```bash
dig +short TXT "_dnslink.$FLOW_DOMAIN"
docker compose exec -T ipfs ipfs resolve "/ipns/$FLOW_DOMAIN"
```

Результат должен указывать на закреплённый CID. DNSLink связывает постоянное имя с версией содержимого, но не заменяет A/AAAA-запись для доступа браузера к серверу. [Описание DNSLink](https://docs.ipfs.tech/concepts/dnslink/).

## 6 Запустите API и HTTPS

```bash
docker compose run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose up -d flow caddy
docker compose ps
docker compose logs --tail=80 flow caddy
```

Caddy получает и продлевает сертификат для указанного домена, если DNS и внешние порты настроены правильно. [Условия автоматического HTTPS](https://caddyserver.com/docs/automatic-https).

Откройте `https://ВАШ-ДОМЕН/#minters`. В том же терминале можно проверить:

```bash
curl --fail "https://$FLOW_DOMAIN/healthz"
curl --fail "https://$FLOW_DOMAIN/ipfs-build.json"
curl --fail "https://$FLOW_DOMAIN/api/mints?limit=1&minimum=0"
```

Первый запрос должен показать `mode=mints` и включённый индексатор. Второй — тот же манифест, который вы читали из CID. Третий — ответ вашего API. `/healthz` подтверждает доступность процесса, но не актуальность всей истории: отдельно проверьте статус/ошибки в интерфейсе и продвижение блока или времени индексатора при повторном наблюдении.

В Developer Tools браузера проверьте вкладку Network: рабочие API-запросы должны идти на ваш домен. Для теста используйте новый профиль браузера или очистите данные сайта, чтобы исключить старый кэш. Загрузка страницы не должна требовать Render. Ссылка «OTC» остаётся обычной ссылкой на отдельный Gonka Market.

## 7 Как хранятся данные

| Том | Содержимое |
| --- | --- |
| `flow-data` | База и локальные кэши Flow в `/data/flow` |
| `ipfs-data` | IPFS repo и закреплённые блоки интерфейса |
| `caddy-data` | TLS-сертификаты и состояние ACME |
| `caddy-config` | Состояние Caddy |

Flow начинает с публичного снимка, встроенного в образ, и догружает данные через RPC. `SNAPSHOT_RESTORE=false` отключает загрузку резервного снимка из GitHub; `LOAD_SEED_ARCHIVE=true` оставляет начальное восстановление встроенной истории. Существующая более свежая база не должна заменяться стартовым архивом.

Обычные `docker compose stop`, `start` и `down` без удаления томов сохраняют эти данные. **Не применяйте `docker compose down -v`, если хотите сохранить базу и pin.**

## 8 Резервное копирование

Для согласованной копии работающей SQLite используется её backup API, а не копирование только одного файла базы без WAL:

```bash
umask 077
mkdir -p backups
BACKUP_PATH=$(docker compose exec -T --user 10001 flow python - < backup_db.py)
docker compose cp "flow:/data/flow/$BACKUP_PATH" "./backups/$(basename "$BACKUP_PATH")"
```

Скрипт создаёт отдельный файл и проверяет `PRAGMA integrity_check`. Перенесите копию за пределы сервера. Каталог `backups` и Docker repo с идентичностью IPFS или сертификатами Caddy не публикуйте в Git/IPFS.

Интерфейс можно сохранить отдельно как публичный CAR-архив:

```bash
docker compose exec -T ipfs ipfs dag export "$CID" > "./backups/ui-$CID.car"
```

Сохраните также текущий CID, `.env`, конфиги и использованные версии образов. CAR содержит статическую сборку, а не живую базу API.

### Восстановление базы на новом сервере

Используйте новый пустой том и не запускайте Flow до восстановления. Поместите проверенную копию в локальный `backups`, выполните `docker compose create flow`, затем замените имя файла в команде:

```bash
docker compose run --rm -T --no-deps \
  -v "$PWD/backups:/restore:ro" \
  --entrypoint python flow - /restore/flow-ВАША-ДАТА.sqlite3 < restore_db.py
docker compose up -d flow
```

Скрипт откажется перезаписывать существующую базу или соседние WAL/SHM-файлы и проверит целостность копии. Он не заменяет экспорт остальных Docker-томов. IPFS-интерфейс можно повторно добавить из исходных файлов либо импортировать из CAR и проверить наличие pin.

## 9 Обновление и откат интерфейса

Повторите сборку из шага 3 в новые каталоги исходных файлов и результата. Для обновления самого приложения сначала выберите и проверьте новый `FLOW_IMAGE`, сохраните резервную копию базы и конфиги. Затем выполните `docker compose pull flow` и `docker compose up -d flow`; извлекайте статику уже из контейнера нужной версии. Автоматического перехода на `latest` здесь нет.

Добавьте новую сборку в IPFS, проверьте её манифест и pin. Только после этого поменяйте TXT DNSLink на новый CID. Домен и адрес API не меняются. Учитывайте DNS/браузерный кэш; сверьте фактически выдаваемый `ipfs-build.json`. Прежний CID пока оставьте закреплённым.

Для отката интерфейса верните прежнее значение TXT. Это не откатывает базу или Docker-образ API: совместимость версии интерфейса с API проверяется отдельно. Старые pin удаляйте только после проверки новой версии и срока отката.

## 10 Если сайт не работает

| Симптом | Что проверить |
| --- | --- |
| Нет HTTPS | A/AAAA, доступность 80/443, логи Caddy, отсутствие другого сервера на этих портах |
| HTTPS есть, интерфейс не найден | TXT DNSLink, разрешение имени внутри IPFS, наличие нужного pin |
| Интерфейс есть, API возвращает 502 | Контейнер Flow и его логи, первоначальное восстановление снимка |
| Интерфейс обращается к Render | Пересборку под свой origin, фактический CID в DNSLink и браузерный кэш |
| Данные отстают | Ошибки RPC/индексатора, доступ в интернет, лимиты RPC и место на диске |
| После перезапуска пропала история | Сохранность `flow-data` и прежнего `STACK_NAME` |

`init-ipfs.sh` разрешает DNSLink только своему hostname и включает `Gateway.NoFetch`, чтобы HTTP-шлюз не скачивал произвольные чужие CID. Caddy также закрывает публичные `/ipfs`, `/ipns`, `/api/v0` и WebUI. Это сайт одного проекта, а не открытый общий IPFS-шлюз. [Настройки Kubo](https://github.com/ipfs/kubo/blob/v0.43.1/docs/config.md).

## Версии и степень проверки

В комплекте: Flow по digest выпуска 27 октября; Kubo `v0.43.1`; Caddy `2.11.7`. Версии Kubo и Caddy сверены с официальными releases на дату гайда. В release notes Kubo сообщается о завершении работы команды Shipyard над проектом 30 сентября 2026 года; перед постоянным размещением следует проверить актуальную поддержку и исправления у проекта. [Kubo releases](https://github.com/ipfs/kubo/releases), [Caddy releases](https://github.com/caddyserver/caddy/releases).

Локально проверяются сборка интерфейса с собственным API, контрольные суммы статических файлов и разбор Compose. Этот комплект не является результатом запуска на вашем сервере: реальные загрузка образов, DNSLink через Kubo, выпуск TLS, резервное копирование и восстановление на Linux требуют проверки на целевом хосте. Команды выше предназначены для оператора сервера; подготовка гайда не выполняет их автоматически.

Дополнительные первичные источники: [Kubo в Docker](https://docs.ipfs.tech/install/run-ipfs-inside-docker/), [маршрутизация Caddy](https://caddyserver.com/docs/caddyfile/directives/handle), [reverse proxy Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).
